# Experiments — methodology and results

> **🇵🇱 Wersja polska:** [EKSPERYMENTY.md](EKSPERYMENTY.md)

This document describes how decision quality is measured in the complaint
handling engine and what the experiments actually teach us. It complements the
README with the engineering context: not just "what percentage", but **why**
the number looks this way and what follows from it.

## Dataset

- 40 mock customer complaints (`datasets/inbox/CASE-0001..0040.json`): damaged
  package, missing item, wrong item, lost parcel, third-party claims, abuse,
  ambiguous cases.
- Per-case ground truth (`datasets/expected/`): expected decision
  (`ACCEPT` / `REJECT` / `HUMAN_REVIEW`), `requires_human` flag, policy refs.
- The dataset was authored by an **isolated agent** that received only the
  domain specification and formats — no knowledge of the implementation.
  This keeps test cases unbiased by familiarity with the solution (avoiding
  the classic "tests written by the code author" trap).
- Groups A–H of 5 cases each localize quality drops per category.

## Metrics

- **Decision accuracy** — share of cases where `final_decision ==
  expected_decision`. `TECHNICAL_FAIL` (provider outage, timeout) counts as an
  error — in production it would be a bad outcome for the customer too.
- **Human-path accuracy** — whether cases needing a human actually went to
  review, and automatable ones did not.

## Two evaluation harnesses

| | batch-eval | eval-native |
|---|---|---|
| Mechanism | webhook → loop of 40 cases through happy path → accuracy report | native n8n Evaluations (Evaluation Trigger + Evaluation node) |
| Result storage | outbox files + `eval-report.json` | Data Table `eval_dataset_v0` (per case) |
| Used for | baseline and regression | demonstrating n8n's built-in evaluation mechanism |

Both harnesses call the same happy path, so decisions are comparable; they
differ in how results are collected.

## Run history

### Runs #1–#2: evaluation as a diagnostic tool (92.5% → 95%)

The first full run produced 3 mistakes, all conservative (expected ACCEPT →
system said HUMAN_REVIEW). Diagnosis from model reasoning: **the input lacked
the product price and delivery time**, while ground truth assumed them. A
dataset defect, not a model defect.

The fix was architectural: an order-system mock (`datasets/orders.json`) plus
an Order lookup node enriching each case before LLM reasoning. Additionally the
Decision router got a deterministic gate (POL-06: order > PLN 2000 ⇒ human
review enforced in code). Methodological takeaway: missing data is fixed by
integrating with the source system, not by editing customer emails.

### Run #3: baseline 95% (38/40, 0 TECHNICAL_FAIL)

Full knowledge base (12 policies + 10 precedents) entirely in the prompt.

### Runs #4–#5: classical RAG A/B experiment (82.5%)

Research question: *does classical RAG (bge-m3 embeddings, cosine similarity,
top-k chunks appended to the prompt) preserve decision quality?*

| Run | rag_top_k | Harness | Accuracy |
|---|---|---|---|
| #4 | 6 | eval-native | 82.5% (33/40, 3× TECHNICAL_FAIL) |
| #5 | 10 | batch-eval | 82.5% (33/40, 2× TECHNICAL_FAIL) |

Takeaways:

1. **RAG costs ~12 p.p. vs the full knowledge base** — on a KB small enough to
   fit in context entirely. Retrieval drops rules that turn out to matter later
   in the reasoning (e.g. the abuse rule for a case that looks standard at
   first glance).
2. **Widening top-6 → top-10 changed nothing.** Context width was not the
   bottleneck. The recurring misses are the same borderline cases: CASE-0018
   (expected HR, system ACCEPT), CASE-0034 and CASE-0037 (expected ACCEPT,
   system HR). The model oscillates at the decision boundary — variance, not
   missing rules.
3. Next-step hypotheses: always append the fallback policy POL-12 (and the
   abuse policy POL-10) regardless of retrieval; alternatively chunkless RAG —
   retrieval over structured fields (category, value, deadline) instead of text
   similarity.

### Run #6: official full run after harness fixes (85%)

After a series of harness repairs (migration to Extract from File, flat-result
parser, retry with backoff on OpenRouter 429s, loop pacing, crash resumability,
timezone and rounding fixes), the full flow ran end-to-end: webhook → 40 cases
→ report generated by the workflow itself (`eval-report.json`), zero manual
computation.

Result: **decision accuracy 85% (34/40)**, human-path accuracy 85%, 0 stale
results. 6 mismatches: 2× TECHNICAL_FAIL (LLM provider incident during the test
day — counted as errors), 4 genuine decision differences including the
recurring CASE-0018 and CASE-0034/0037.

Comparing #5 vs #6 (identical top-10 configuration): 82.5% vs 85% — a ±2.5 p.p.
spread confirming that a single run measures the result with model-variance
tolerance, and conclusions should be drawn from recurring case patterns rather
than single numbers.

## Regression

The `claims-demo-report` workflow computes accuracy from result files (no LLM
calls) and compares it against configured thresholds. Target state: run on
every prompt/rule change, PASS/WARNING/FAIL like CI.

## Limitations (honestly)

- One run = one sample; on 40 cases a few p.p. difference can be variance.
  Conclusions here are drawn from recurring patterns (same cases, same error
  direction), not from single numbers.
- Mock dataset, Polish language, e-commerce domain. Generalizing to another
  domain requires its own dataset — the machinery itself (harnesses, gates,
  Claim Case history) is domain-independent.
